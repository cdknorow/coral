# Security migration and retired-feature review

This specification records the security audit and migration boundaries for Coral. It distinguishes observed source reachability from proven production use. A reachable route or code path is not evidence that an operator uses it. It also distinguishes approved database-encryption work from proposed removal of other features. No existing credential or user data is deleted, rotated, revoked, or migrated without an explicit operation.

## Findings and dependency map

### Proxy, provider keys, and cost data

The #2002 runtime retirement removes proxy route/CONNECT registration, CA generation, provider-key loading, and proxy URL/base-environment launch injection. Historical proxy tables and cost readers remain available so transcripts and historical accounting continue to work. Existing CA/key files are retained and are not deleted automatically.

### Connected Apps, secrets, and workflow propagation

The #2002 runtime retirement removes OAuth/token/profile/refresh/revoke routes and startup registries while leaving legacy rows untouched. Unknown `connections` fields remain in old workflow JSON, but a workflow containing them fails before execution with no credential lookup or environment injection. A future integration would require a separately approved metadata-only/keychain design.

### Slack scopes

The built-in Slack OAuth provider requests `channels:read` and `chat:write`. This is a write-capable connected-app scope and should retire with Connected Apps unless a separately approved Slack integration defines data classification and least-privilege scopes. Existing generic Slack webhook notifications are a different path and must be reviewed independently.

### Remote access, QR, and query/session behavior

The current default config binds `CORAL_HOST` to `0.0.0.0`. Before binding, `applyPrivacySettings` reads `user_settings.remote_access_enabled`; a saved value equal to `false` forces `127.0.0.1`. `/api/system/privacy` reports `remote_access_enabled`, `remote_access_effective`, `remote_access_restart_required`, and `effective_host`. This is an implemented mitigation from privacy work #1824-1826 and must remain intact while policy is decided. The ability to enable remote access, default-on behavior, CORS same-origin handling, API-key query use, QR reachability, and session lifetime need explicit policy and integration tests.

`auth/keystore.go` uses a persisted API key, a session cookie with `sessionMaxAge = 24h`, LRU sessions, and IP rate limiting. `auth/middleware.go` accepts bearer/query credentials according to its local/remote rules. The QR path is reachable from settings and currently exposes the connection URL while the key is displayed separately; it must not be described as a combined secret payload without verifying the generated bytes. This design does not establish whether query tokens are logged by clients, proxies, browser history, or request metrics. Add tests and documentation before making security claims.

Options:

1. Retain and harden: preserve the setting gate, default local-only, require explicit opt-in, remove query-token auth, shorten/revoke remote sessions, bind QR to an authenticated one-time flow, and test listener/CORS/API-key behavior.
2. Retire remote features: force loopback, remove QR/mobile/remote-board surfaces, keep local dashboard/native app/CLI workflows and local authentication. This requires an operator decision because source reachability does not prove the feature is unused.

### Remote boards

`routes/board_remotes.go` validates registered remote URLs and proxies board reads; `background/remote_poller.go` performs outbound polling and nudges local agents. `remote_board_subscriptions` rows must be preserved during either option. If retired, stop polling and route registration without contacting or deleting remote servers.

## Approved database encryption architecture

Task #1992 implements optional SQLCipher storage for both runtime SQLite databases: the primary `sessions.db` and separate `messageboard.db`. SQLite WAL, SHM, rollback journal, temporary journal, and migration outputs must use the encrypted driver; file names, sizes, timestamps, permissions, and directory metadata remain visible. Transcripts, logs, artifacts, uploads, screenshots, CA files, `api_key`, shell history, and other files outside those DBs remain out of scope.

Bootstrap metadata is `~/.coral/security.json` and contains only `database_encryption` (`disabled`, `key_file`, or `password`) and optional `key_file` path. It never stores a password or derived key. `key_file` uses an owner-only `~/.coral/.db_key` created atomically with restrictive permissions and never overwrites an existing file or follows a symlink. Existing key files must be regular files with mode `0600`; Unix builds also require current-user ownership and open with `O_NOFOLLOW` to avoid a check/open replacement race. Non-Unix builds enforce regular-file and mode checks; owner/ACL enforcement remains platform-specific because Go has no portable owner API. Missing/wrong key fails closed; it never recreates a database or falls back to plaintext. Password mode prompts before DB open through the supported CLI TTY surface. The macOS tray uses a Cocoa secure text field before database open. Linux/Windows tray and webview currently have no secure native secret-input primitive and fail closed for password mode; launch-coral is a CLI surface with the same secure TTY prompt as coral. Key-file mode is the supported unattended mode there. Browser settings use only `GET/PUT /api/system/database-security` mode metadata and never receive password/key material.

Encrypted builds require the vetted SQLCipher driver and FTS5 build configuration. Plaintext default builds remain compatible and report unavailable encrypted capability when the codec/build is absent. The driver/build/license/CVE matrix must pass before release.

## Migration, rollback, and recovery

Existing plaintext DB migration is explicit (`CORAL_DB_ENCRYPTION_MIGRATE=1|true`, for example `CORAL_DB_ENCRYPTION_MIGRATE=1 coral`). It runs under the per-home lock before listener/services, prepares and verifies both database exports before changing either canonical path, then swaps both while retaining `.plaintext-backup` files. A failed preparation leaves both sources unchanged; an install failure rolls back completed swaps. A durable `.db-migration-state.json` marker records only phase and database paths before swaps, after backups, and during install. Startup refuses to open databases while that marker exists, preventing a process crash from opening mismatched generations; preserve temp/backup files, restore one consistent pair, remove the marker, and rerun the explicit command. WAL/SHM/journal state and free space must be checked. Backups remain plaintext until the user explicitly deletes them and therefore retain residual at-rest risk.

The normal Makefile, stress/frontend harnesses, and release workflow build with the `fts5` tag, CGO enabled, and OpenSSL development headers/libraries; this is required by the SQLCipher driver and makes `feature_available` true in shipped builds. The selected driver is `github.com/0xCarbon/go-sqlite3` v1.15.1 (module metadata checked 2026-10-01), a mattn/go-sqlite3-compatible database/sql driver bundling a pinned SQLCipher amalgamation and linking OpenSSL. It applies the key before any schema pragma, verifies `cipher_version`, and fails closed if the linked library lacks the codec. Password mode derives a fixed 32-byte raw key with salted PBKDF2-HMAC-SHA256 (600,000 iterations); key-file mode uses the high-entropy file material directly when it is a generated 32-byte key. The resulting raw key is passed to the driver's `_key` open parameter, so every pooled connection is keyed before schema access. It bundles SQLCipher 4.17.0 (pinned source commit `810db22f575ee7cf94ea96a3e91622b5fcece3dc`) / SQLite 3.53.3 with `SQLITE_SOURCE_ID` ending `d4c0e51e4aeb96955b99185ab9cde75c339e2c29c3f3f12428d364a10d78alt1`, and requires Go 1.21+, CGO, a compiler, and OpenSSL development headers/libraries. Its published license is MIT for the Go binding, with bundled SQLCipher BSD-style and SQLite public-domain notices; release packaging must preserve those notices. SQLCipher 4.x files are incompatible with 3.x without migration. No claim of zero CVEs is made: release owners must review the driver and SQLCipher/SQLite advisories before publishing.
The 0xCarbon fork has a tagged v1.15.1 release (2026-08-17); its recent commits include exact `_key` spelling checks, vendored SQLCipher provenance, and CodeQL workflow changes. Upstream mattn/go-sqlite3 is more active (v1.14.52 and commits through 2026-09-28) but does not ship SQLCipher; linking it to an official SQLCipher system library would require a separately maintained system package and platform-specific codec build. The fork is therefore the reproducible first-release choice, with its smaller maintainer community recorded as a residual support risk rather than conflated with upstream mattn support.

OpenSSL is dynamically linked. Release packaging copies `libcrypto.so.3` beside Linux binaries and sets `$ORIGIN`, copies the OpenSSL DLL beside Windows binaries, and builds a true arm64+x86_64 universal `libcrypto.3.dylib` from matching Homebrew `openssl@3` prefixes before rewriting executable load paths to `@rpath`/`@loader_path`. The macOS workflow builds each slice against its matching headers/library and fails if the x86_64 Homebrew toolchain is unavailable. The Linux, Windows, and macOS jobs resolve runner package versions at execution time, so each job must record actual OpenSSL package metadata and run the current advisory check before accepting an artifact. The current host reports LibreSSL 3.3.6 and is not evidence for any shipped OpenSSL version. SQLCipher uses OpenSSL for local database codec operations; advisories specific to TLS/QUIC server paths are not automatically reachable in Coral, but every packaged libcrypto still requires version and vendor-backport review. Clean-machine validation must still execute each packaged artifact on supported Linux, Windows, and macOS amd64/arm64 runners; local validation confirmed the prior arm64-only/absolute-path defect and cannot provide the x86_64 OpenSSL slice on this host.
`THIRD_PARTY_NOTICES_SQLCIPHER.md` is copied into every platform package and app payload. It points to the exact binding, SQLCipher/SQLite, and OpenSSL license sources; platform OpenSSL package notices must accompany the copied library. An OSV query for the pinned Go module returned no records on 2026-10-01, but this is not a zero-CVE conclusion; release review must check current OpenSSL, SQLCipher, and SQLite advisories for the actually packaged versions.

The packaged-binary gate is `tests/release/verify_encrypted_bundle.sh` (Linux/macOS) and `tests/release/verify_encrypted_bundle.ps1` (Windows). Each verifier enumerates the shipped CLI, tray/app, and hook executables, checks the bundled native crypto dependency (including universal macOS slices and loader paths), and runs `coral --encryption-self-test`. That self-test writes and reopens sentinels through the real sessions and board stores, confirms ciphertext on disk, and rejects a wrong key. A local arm64 extracted package passed with its bundled dylib; removing that dylib and omitting an executable both produced deterministic failures. Intel macOS, Linux, and Windows execution remain CI-only evidence until their runners complete.

`tests/release/verify_openssl_attestation.sh` additionally binds the advisory decision to the checked-in `tests/release/openssl_policy.tsv`, exact copied library hash, and package identity. macOS records and policy-checks independent arm64 and x86_64 source versions, both slice-input hashes, and the final universal-library hash; Linux records the package owning the source library before copying; Windows records the package/DLL identity. Only policy rows for numerically supported patched branches or exact reviewed vendor backport revisions are accepted; unknown vendors, branches, labels, and identity or slice mismatches fail closed.

The implemented maintenance flow supports explicit plaintext-to-encrypted migration only. Encrypted key rotation and encrypted-to-plaintext disable/decrypt are intentionally unsupported because the current CLI has no safe old-key/new-key input or rekey transaction; the settings API rejects those active-mode transitions with `migration_required` rather than stranding the installation. Do not advertise a password/key change or decrypt procedure until a dedicated offline command has been implemented and tested. There is no forgotten-password backdoor. Lost password/keychain item requires a user-managed backup or data discard. Key file plus DB theft is not protection against a thief who obtains the entire data directory or a same-user/compromised process; it mainly protects DB-only copies. Encryption does not fix local authorization, subscriber/query trust, process compromise, memory exposure, or external transcript/artifact leakage.

## Acceptance gates and deployment boundaries

1. Source guards prove retired proxy/Connected Apps/remote paths are absent only after their separate policy decisions; no user credentials/data are deleted by default.
2. Encryption tests cover plaintext default compatibility, encrypted primary/board reopen, stock SQLite unreadability, wrong/missing/cancelled key, key permissions/path/symlink safety, migration integrity and rollback, WAL/journal handling, restart, concurrent owner lock, schema compatibility, and supported macOS/Linux build variants.
3. Startup tests prove no listener/background service starts before both DBs unlock and no password/key appears in argv, env, logs, API responses, board messages, or artifacts.
4. API tests prove mode-only database-security mutation, saved/effective/restart state, feature availability, unlock surface, and explicit migration-required errors for unsafe in-place mode changes.
5. Native, TTY, and headless behavior is documented honestly; UI never implies a browser can unlock a pre-listener database.
6. Final release requires independent verification, migration backup disclosure, driver licensing/CVE review, and an explicit operator decision on remote/proxy/Connected Apps retirement. No commit, push, release, production migration, or live restart is implied by this document.
